# fea-translator

Turns an **FEA study** (one solid part, a material, an analysis, supports and loads on chosen faces) into a [Gmsh](https://gmsh.info) mesh, a [CalculiX](http://www.calculix.de) input deck and checked results, deterministically. It includes a command line (`feat`), a Python API and an MCP server (`feat-mcp`), so LLM-based tools can set up analyses as studies and get the numbers back with their checks.

It is the FEA counterpart of [build123d-translator](https://github.com/feranick/build123d-translator): an LLM writes the study (the flexible part), the translator computes everything else (which mesh faces, which nodes, consistent nodal loads, element face numbers, the deck), and a checker confirms the result: closed-form benchmarks, equilibrium and heat balance on every run, expected values, and mesh convergence. Parts are STEP files or build123d-translator goals, so the same face conventions select CAD features and boundary conditions.

Analyses: **linear static** (displacements, von Mises stress, reactions, safety factor), **modal** (natural frequencies), **linear buckling** (load factors), **steady heat transfer** (temperatures, heat flows; with `stress: true`, thermal stresses), **DC electric conduction** (terminal currents, resistance, power, current density), **electrostatics** (charges, capacitance, field, margin to breakdown), **Joule heating** (electric, then thermal, optionally stresses), **bolted joints** (gaskets and pretensioned bolts: leak and lift-off pressures) and **assemblies** (parts in contact, bolts and nuts, static and modal steps).

## Install

```bash
cd ~/Desktop/fea-translator
python3 -m venv .venv && source .venv/bin/activate        # Python 3.10+
pip install -e ../llmt-runtime                             # the translators' shared runtime, first (or: pip install -r requirements-standalone.txt)
pip install -e ".[mesh,mcp,test]"                          # numpy, scipy, matplotlib, gmsh, MCP SDK, pytest
pip install -e ".[render]"                                 # optional: VTK pictures (PyVista), "quality": "high"
pip install -e ../build123d-translator                     # optional: parts as goals
```

VTK draws offscreen, so a server without a display needs one of: a GPU driver's EGL (`sudo apt install libegl1`), OSMesa (`sudo apt install libosmesa6`), or Xvfb (`sudo apt install xvfb`: the renderer then runs under `xvfb-run -a`). `feat status` shows what it found under `render` once a picture has been drawn. Matplotlib needs nothing more.

On **Linux ARM (aarch64**, e.g. DGX Spark) PyPI has no Gmsh wheels, so the `mesh` extra skips it; use Ubuntu's (Gmsh 4.12 on 24.04) and link its Python module into the venv (same Python version as the system's):

```bash
sudo apt install -y python3-gmsh
ln -sf /usr/lib/python3/dist-packages/gmsh.py "$VIRTUAL_ENV/lib/python3.12/site-packages/gmsh.py"
```

The executor's shared code (workers, out of memory, the SLURM layer: settings, caps, time limits, `job.sh`, submission, job states, the queue, `jobs`, `cancel`, `extend`; request names, version recording) comes from **llmt-runtime** (`llmt-runtime>=2026.11.09.4`, a floor: any later version works); feat's sizing (threads, memory, time limits) plugs into it as hooks. Inside llm-translators, `llmt install` / `llmt update` / `llmt deploy` install it first from the umbrella's pinned copy.

CalculiX (`ccx`) is a separate program:

- macOS: a Homebrew tap packages current ccx for Apple Silicon (`costerwi/calculix`, see its README for the exact formula name), or build it from source; then `ccx -v` should print the version.
- Linux (Ubuntu/Debian): `sudo apt install calculix-ccx`.

The translator finds `ccx` (or `ccx_2.*`) on the PATH or in `/opt/homebrew/bin`; `FEAT_CCX=/path/to/ccx` overrides. Without CalculiX the package's own reference solver runs static, modal and thermal studies on small meshes (`--solver ref`); buckling needs CalculiX.

```bash
feat status                    # versions; ccx and gmsh found?
pytest -q                      # 105 tests: 83 run anywhere (36 with fake SLURM commands or a fake ccx, 6 of the MCP server, 9 of pictures; two need build123d-translator, one VTK), 21 need ccx (and Gmsh)
feat bench                     # every benchmark, pass/fail against closed-form answers
```

## Use

```bash
feat format > study_format.json          # analyses, materials, bc kinds, selectors, conventions, example
feat validate examples/studies.json      # static checks
feat run examples/studies.json           # mesh, solve, check; files in ~/feat_runs/run_<time>/
feat status ~/feat_runs/run_<time>       # results of a request (finished and still running studies)
feat deck examples/studies.json bracket_static   # the CalculiX deck only
feat bench lame_ring plate_hole          # chosen benchmarks
```

Every command prints JSON; `-` reads the studies from stdin. `feat run` waits for all studies; the MCP `run_studies` returns within about 45 s and leaves long studies `pending` (see below). Output folder: `FEAT_OUT` (default `~/feat_runs`); `FEAT_WORKERS` (2) worker processes, `FEAT_TIMEOUT` (900 s per study), `FEAT_SOLVER` (auto | ccx | ref).

Per study the folder holds `part.step`, `mesh.msh`, `<name>.inp` (the deck; runs with `ccx -i <name>` on its own), `<name>.dat` and `<name>.frd` (CalculiX results; `.frd` opens in CalculiX GraphiX, FreeCAD, or ParaView via ccx2paraview) and `<name>.json` (the results below).

## A study

```json
{"bracket_static": {
  "part": {"goal": {"features": [
      {"kind": "base_box", "params": {"w": 100, "d": 20, "h": 10}},
      {"kind": "hole", "params": {"r": 4, "x": 35, "y": 0}}]}},
  "material": "aluminium_6061_t6",
  "analysis": "static",
  "mesh": {"size": 3},
  "bcs": [{"kind": "fixed", "name": "wall", "faces": {"nx": -1}},
          {"kind": "force", "name": "load", "faces": {"cyl_r": 4, "side": "inner"}, "fz": -200}],
  "probes": [{"name": "tip", "faces": {"nx": 1}}]}}
```

- **Units:** mm, N, MPa; density kg/m³; conductivity W/(m K); film coefficient W/(m² K); heat flux W/m²; heat W; °C; gravity m/s². The deck uses mm, N, s, t, mW; the conversions are in `study.py`.
- **Part:** `{"step": path}` (mm) or `{"goal": ...}` (built with build123d-translator); `{"box": [lx, ly, lz]}` is a structured box mesh without Gmsh (tests, quick checks).
- **Material:** a name (steel, stainless_304, aluminium_6061_t6, titanium_ti6al4v, copper, brass, cast_iron, abs, pla, nylon_pa6; typical values) or `{E, nu, density, k, alpha, yield}`, or a name with overrides `{"name": "steel", "yield": 355}`.
- **Faces** (as build123d-translator): `{nx, ny, nz}` the largest planar face with that outward normal (`at` for the nearest one), `{pts: [[x, y, z], ...]}` the face nearest to each point, `{cyl_r: r}` every cylindrical face of radius r (found by fitting the mesh, so it does not depend on how the STEP describes the surface; `side: "inner"` for holes and bores only, `"outer"` for shafts, bosses and outside fillets, which otherwise match too: a 4 mm hole and 4 mm corner fillets are all `cyl_r: 4`), `{all: true}`; a list is their union. Every result lists what each selector took (`selection`: kind, radius, side, arc, area, centre per face), with a warning when one `cyl_r` takes holes and convex faces together.
- **Boundary conditions:** `fixed`, `slider` (normal displacement zero: symmetry planes, rollers), `displacement` (prescribed components); loads `force` (a total force spread uniformly over the faces' area), `pressure` (normal, positive into the part), `gravity`; thermal `temperature`, `heat_flux`, `heat` (total watts on faces), `convection`; electrical `voltage` (a terminal or electrode; 0 V for ground) and `current` (total amperes into the faces).
- **Electrical** (2026.10.18.1): `electric` (resistivity) and `electrostatic` (permittivity) are solved by CalculiX's steady heat transfer, whose equation is the same (∇·(σ∇φ) = 0 with the potential for the temperature); `joule` runs the electric solve, puts σ|∇φ|² into each element as heat and solves the thermal problem with the study's thermal bcs. `stress: true` on `thermal` or `joule` adds a static solve with the temperatures (expansion from `T_ref`, default 20 °C) and the mechanical bcs. Electrical material data in the library: `resistivity` (Ω m), `permittivity` (relative), `dielectric_strength` (kV/mm); new materials silver, gold, alumina_96, fr4, ptfe. Resistivity is constant (room temperature).
- **Mesh:** `size` (mm; default 1/20 of the bounding-box diagonal), `order` 2 (10-node tetrahedra, default; 4-node ones are far too stiff in bending), `refine: [{at, r, size}]` finer spheres at stress concentrations. `converge: true` reruns at 0.6 × size and reports the change of the main results.
- **Large meshes:** `equation_solver`: `auto` (CalculiX's iterative Cholesky-preconditioned solver above 150,000 nodes for static and thermal, else the direct one), `direct` or `iterative`.
- **Checks:** `expect: [{quantity, value, tol}]` with a dotted path into the results (`max_displacement`, `max_von_mises_nodal`, `frequencies.0`, `critical_factor`, `reactions.wall.fz`, `faces.load.mean_u.uz`, `probes.tip.mean_u.uz`, `heat_flow.base`, `T_max`...).

### Results

| Analysis | Results |
|---|---|
| static | `max_displacement` (+ where, per component), `max_von_mises` (integration points) and `max_von_mises_nodal` (CalculiX's nodal values), with where; `peak_von_mises` (the larger of the two) and `safety_factor` (yield / that peak); `peak_von_mises_off_bc` and `safety_factor_off_bc` (leaving out the material within `stress_band` of supports and loads, where stresses are singular; default two element sizes of the nominal mesh, the same on the `converge` mesh so the value can converge; widen it if it does not); `peak_at_bc` (the supports or loads the peak sits on); `reactions` per support, `faces` and `probes` (area-weighted mean displacement, largest), `applied_force`, `equilibrium_error`, `mass_kg` ; `stress_check` (CalculiX's integration-point stresses against those recomputed from its displacements: `agree`, `max_difference_MPa`, `elements_disagreeing`, `worst_at`, and `elements_within_rounding`: elements where the difference is within what the `.dat`'s 7-digit displacements allow, which are not counted as disagreeing); `stress_probes.<name>` (for each sphere `{name, at, r}` of the study's `stress_probes`: `peak_von_mises_MPa` at the integration points inside, `peak_at`, `mean_von_mises_MPa` (volume-weighted), `max_principal_MPa`, `points`, `elements`, `straightened_elements` and `peak_von_mises_unstraightened_MPa` without them, `peak_von_mises_nodal_MPa`): a local peak, e.g. at one fillet, away from the global maximum |
| modal | `frequencies` (Hz), `mass_kg` |
| buckling | `buckling_factors`, `critical_factor` (critical load = factor × the applied loads) |
| thermal | `T_max`, `T_min` (+ where), `heat_flow` per temperature and convection boundary (W, into the part), `heat_balance_error`, `faces` and `probes` (mean, max, min temperature) |
| electric | `terminals` (per terminal: `V`, `I_A` into the part), `resistance_ohm` (two terminals), `power_W`, `current_balance_error`, `max_current_density_A_mm2` (+ where) and `max_current_density_off_terminals_A_mm2`, `V_max`, `V_min`, `faces`/`probes` mean potential |
| electrostatic | `terminals` (`V`, `Q_C`), `capacitance_pF` (two voltage levels), `energy_J`, `charge_balance_error`, `max_field_kV_mm` (+ where) and `max_field_off_electrodes_kV_mm`, `breakdown_safety_factor` (dielectric strength / peak field, also off the electrode edges) |
| joule | the thermal results, `electric` (the electric results), `joule_heat_W` and `joule_check_error` (element-wise heat against the electric power) |
| thermal or joule with `stress: true` | `stress`: the static results (displacements, von Mises peaks, safety factors, reactions) of the thermal expansion |

Every run also returns `checks` (the `expect` list, pass or fail), `passed`, `warnings` (unbalanced reactions or heat; a result changing by more than 5 % on a finer mesh; a peak at a support or load; a peak that grows on a finer mesh while the displacement has converged, i.e. a singularity; a `cyl_r` that took holes and fillets together), mesh size and counts, times, and the files.

### Joint studies

`"analysis": "joint"` (CalculiX only) models a bolted, gasketed joint: several parts in contact, a gasket law between two flange faces, pretensioned bolts, and one pressure or force raised in steps until the joint leaks and lifts off (a cover's relief pressure).

```json
{"analysis": "joint", "mesh": {"size": 6},
 "parts": {"body":  {"part": {"step": "s50_body.step"}, "material": "cast_iron"},
           "cover": {"part": {"step": "s50_cover.step"}, "material": "steel", "move": [0, 0, 0]}},
 "bcs": [{"kind": "fixed", "name": "feet", "faces": {"part": "body", "nz": -1}},
         {"kind": "pressure", "name": "inside", "p": 2.0,
          "faces": [{"part": "cover", "nz": -1, "at": [0, 0, 5]}, {"part": "body", "cyl_r": 60, "side": "inner"}]}],
 "gaskets": [{"name": "cover_gasket", "faces": {"part": "cover", "nz": -1, "at": [75, 0, 10]},
              "with": {"part": "body", "nz": 1, "at": [75, 0, 10]},
              "curve": [[0.05, 2], [0.1, 8], [0.2, 30], [0.3, 60]], "seal": {"stress": 10, "m": 2}, "friction": 0.2}],
 "bolts": [{"name": "cover", "size": "M10", "torque": 40, "pattern": {"center": [0, 0, 22], "pcd": 170, "n": 8},
            "head": {"part": "cover", "nz": 1}, "thread": {"part": "body", "depth": 15}}],
 "sweep": {"bc": "inside", "steps": 12}}
```

- **Parts**: `parts` replaces `part`; each has its own material, an optional `move` [dx, dy, dz] and an optional `mesh` (its own `size`, `refine`, `min_size`, `curvature` over the study's `mesh`: a detailed part can be meshed coarser, e.g. `{"size": 10, "min_size": 6, "curvature": 0}`); every face selector names its `part`. Parts are meshed separately (same element order) and meet only through gaskets and bolts.
- **Gaskets**: `faces` is the gasket side (the contact slave), `with` the mating flange face. Face-to-face penalty contact with a linear pressure-overclosure law and friction (0.2): `stiffness` (MPa/mm), or `curve` [[closure mm, stress MPa], ...] (the data sheet's loading curve), which becomes its secant at the gasket's mean stress under the preload (the preloads of the bolts nearest to it over its area; `gaskets.<name>.law` gives it). CalculiX ignores a tabular law in face-to-face contact (the parts pass through each other) and node-to-face contact does not suit 10-node tetrahedra. The secant puts the preload on the curve on average; on unloading (pressure) a real gasket is stiffer than its loading curve, so the secant lies between its loading and unloading stiffness. A warning tells when the preload stress lies beyond the curve, or when the gasket's mean preload stress is far from the secant's. The gasket is modelled as the contact law: its thickness is not meshed, so the flange faces should touch (or be `move`d to touch) in the CAD.
- **Bolts**: `size` M3-M36 (ISO 898-1 stress area, ISO 273 medium clearance hole, ISO 7089 washer; `hole_d`, `washer_d` override), `preload` N or `torque` N m (P = T / (k d), k 0.2), positions `at` (points on the axes) or `pattern` {center, pcd, n, start_deg}; `head` the bearing face under the head, `nut` the bearing face under the nut, or `thread` {part, depth} for a tapped hole (the bore over the engaged depth). Each bolt is a spring (k = E A_s / grip) from head to nut, each end tied to the mean displacement of its bearing annulus (or the engaged bore); the preload acts across a cut at the head (an equation with a reference node that takes the preload in step 1 and is then locked), so the bolt force follows the joint. Bolts carry no shear or bending: friction at the gasket holds the parts sideways.
- **Steps**: step 1 the preload (with the constant loads), then `sweep.steps` steps raising the swept bc to its value (the last step's).
- **A preload that converges**: before the gasket is pressed, a part held only by bolts and gaskets has no stiffness (the gasket gives none at first touch, friction none without pressure) and can slide or rock about its bolt line. So every part that no support holds gets weak springs to ground (6 well-spread nodes, 3 directions, each 1e-6 of the softest bolt's stiffness; `stabilisation` in the results gives their force per step, with a warning above 1 % of the preload); the preload starts at 5 % of its value; the friction's stick slope is 100 times lower in the preload step (`*CHANGE FRICTION` restores it in step 2); and `gaskets.<name>.gap_mm` with a warning tells when the gasket's faces do not touch at the start.
- **Failing fast**: while CalculiX runs, its `.sta` and `.cvg` files are read every 5 s. Contact chatter (the number of contact elements swinging up and down over 16 iterations of an attempt), a contact that has not settled after 25 iterations of an increment CalculiX has already cut back (its count still varying by a factor 3), or an increment failing 3 attempts stops the run with the reason, e.g. `preload did not converge: contact chatter (30964 contact elements switching, 66000 to 96964; ...)`, instead of running to the time limit. A run stopped (or out of time) after the preload keeps the steps it finished: `stopped` and a warning say where.
- **Leak and lift-off**: at every step the contact pressure at the gasket nodes gives the ring stress (the strongest closed ring of gasket nodes around the pressurized edge: the minimax path from the inner edge, the one nearest `inner_at` or the pressure, to the outer edge). Leak: ring stress below the sealing stress (`seal.stress`, or `m` x p, whichever is larger); lift-off: ring stress 0 (an open path across: a cover acting as a relief valve). Both interpolated between steps; `{"above": max}` when not reached.
- **Results**: `leak.<gasket>`, `lift_off.<gasket>` (MPa for a pressure sweep, N for a force), `gaskets.<name>` (area, edges, `preload` stresses and force), `bolts.<name>` (preload, stiffness, positions, max force), `steps[]` (load, bolt forces, gasket ring/min/max/mean stress, contact fraction, force, leak, open), `preload_balance_error` (gasket force against the bolt preloads), `selection`.
- **Not modelled**: the pressure reaching into an opening gasket (leaks slightly earlier), bolt bending stresses, thread stripping, gasket creep relaxation; no `converge`.
- **Pictures** (`images`, `render_images`): `images: true` draws the setup (each support, load and gasket in its colour, the bolts as lines), each gasket's stress at the preload and at the last step (viewed face on, from 0 to the peak, the sealing stress marked on the colour bar), and the deformed assembly. Joint views take `step` (1 = the preload, up to `sweep.steps` + 1; default the last) and the field `gasket_stress` (on a gasket: `surface: <gasket>`); `displacement`, `ux`/`uy`/`uz`, `von_mises` and `max_principal` (each part with its material) work as in static studies. Every run saves every step in `state.npz`, so `render_images` can draw any step later, e.g. the step before lift-off.
- **Bolt forces**: each spring's stiffness times its stretch; at the preload it equals the preload (`bolt_preload_error`).
- **Benchmarks** (the test suite skips them unless `FEAT_SLOW_TESTS=1`: about 35 min together with CalculiX; `run_benchmarks` runs them always) (joint diagram, C = k_b / (k_b + k_j)): `joint_pull` (two blocks, the base held on its bottom face where the nut bears, an M12 bolt, a pull: preload force 3 %, lift-off F = P / (1 - C) 10 %) and `joint_cover` (a cover with a spigot on a ring, 8 M12 bolts, internal pressure: leak and lift-off pressures 15 %) and `joint_two_bolt` (a plate on two M10 at 25 N m on a gasket whose curve starts with no stiffness: the preload converges, the gasket carries the bolts' preload).

### Assembly studies

`"analysis": "assembly"` (CalculiX only) is the general multi-part study; a joint study is an assembly whose steps are a preload and a sweep. It takes the joint's `parts`, `bcs`, `gaskets` and `bolts`, and:

```json
{"analysis": "assembly", "mesh": {"size": 4},
 "parts": {"shaft": {"part": {"step": "shaft.step"}}, "sleeve": {"part": {"step": "sleeve.step"}},
           "impeller": {"part": {"step": "impeller.step"}, "material": "cast_iron"}},
 "bcs": [{"kind": "fixed", "name": "bearings", "faces": [{"part": "shaft", "cyl_r": 20, "at": [0, 0, 40]}]},
         {"kind": "force", "name": "side", "faces": {"part": "impeller", "cyl_r": 80}, "fy": 310}],
 "contacts": [{"name": "hub_sleeve", "faces": {"part": "impeller", "nz": -1, "at": [0, 18, 300]},
               "with": {"part": "sleeve", "nz": 1}, "friction": 0.2},
              {"name": "sleeve_shoulder", "faces": {"part": "sleeve", "nz": -1}, "with": {"part": "shaft", "nz": 1, "at": [0, 20, 260]}},
              {"name": "bore", "faces": {"part": "sleeve", "cyl_r": 15, "side": "inner"}, "with": {"part": "shaft", "cyl_r": 15},
               "clearance": 0.01}],
 "nuts": [{"name": "nut", "size": "M20", "torque": 120, "at": [[0, 0, 340]], "bears_on": {"part": "impeller", "nz": 1},
           "thread": {"part": "shaft", "depth": 16}}],
 "probes": [{"name": "tip", "faces": {"part": "shaft", "nz": 1, "at": [0, 0, 360]}}],
 "steps": [{"kind": "preload"}, {"kind": "static", "loads": ["side"]}, {"kind": "modal", "modes": 6}]}
```

- **Contacts** `[{name, faces, with, law, friction, clearance}]`: face-to-face penalty contact between two parts' faces. `law` `hard` (default: a linear penalty of 10 E / h, the softer part's E and the finer element size), `{"stiffness": MPa/mm}`, or `bonded` (tied in every direction, CalculiX's TIED law: a one-piece reference, or a fallback when friction will not converge). `friction` 0.2 (0: frictionless). `clearance` (mm) sets the pair's initial gap, whatever the CAD shows (> 0, face-to-face contact with `*CLEARANCE`), or an interference fit (< 0): the slave face's nodes are moved by it along their outward normals, into the master, and the pair uses node-to-surface contact (`contact_type` in the results). CalculiX's face-to-face contact with an interference on curved quadratic faces settled on states with the interference not enforced, or did not converge, however it was made; node-to-surface converged in seconds within 1.4 % of Lame (`tools/interference_matrix.py`).
- **Nuts** `[{name, size, preload | torque, at, bears_on, thread {part, depth}}]`: a nut on a meshed shaft. It presses `bears_on` (e.g. the impeller hub's face) and grips the shaft's thread over `depth` beyond it, pushing the two apart; the clamp runs through the parts and contacts in between to the shaft's shoulder. The nut is a stiff connector (10 E A_s / d); the shaft carries the tension in its own mesh. `preload` is the axial clamp force; `torque` gives it with k 0.2.
- **Steps** `[...]`, in order: `{kind: preload}` (first; added by itself when there are bolts or nuts), `{kind: static, loads: [bc names], scale, name}`, `{kind: sweep, bc, steps}` (at most one), `{kind: modal, modes}` (after a static step: the frequencies of the state that step left, as a separate linear CalculiX `*FREQUENCY` run with the bonded pairs tied whole and every other pair tied where it was closed then (its closed slave nodes, a nodal `*TIE`; open everywhere: free), gaskets closed over half their area tied, and the bolts and nuts at their preloaded length; a closed pair that was partly slipping is tied too, with a warning that the frequencies are an upper bound there. A part with no tied path to a support (bolts and nuts, axial springs, do not count) floats on feat's stabilisation springs: its rigid-body modes are asked for on top of `modes` and left out of `frequencies_Hz` (`floating_parts`, `rigid_body_Hz`), with a warning that the frequencies are not the assembly's; any frequency below 1 Hz is warned of. A `PERTURBATION` frequency step after frictional contact kept no tangential stiffness in CalculiX: the clamped beam's first mode came out at 0 Hz). A load bc no step names acts in every step from the preload on; a static step adds the loads it names (x `scale`); loads do not carry over from one static step to the next. Modal steps run single-threaded and need every part's density.
- **Probes** `[{name, faces}]`: the faces' mean displacement at every step (e.g. a tip deflection), from CalculiX's printout of their nodes.
- **Results**: `steps[]` (one per static, preload and sweep step): `contacts.<pair>` (`force_N`: on a flat face the element forces at the slave face's nodes, from the displacements with the part's material, which balance the contact force on it exactly (`force_from: element forces`; summing a stiff penalty's nodal pressures was up to 2x off, CalculiX's section force (`SOF`, from extrapolated stresses) 7 %), on a curved face the pressures' integral (`force_from: pressures`, also `pressure_force_N`); `shear_N`, `max_pressure_MPa`, `mean_pressure_MPa`, `closed_fraction`, `stick_fraction` (of the closed area, shear below mu x pressure), `max_opening_mm`, `max_slip_mm`), `bolts.<name>` (nut forces positive in compression), `gaskets`, `probes.<name>` (`ux`, `uy`, `uz`, `u`), `parts.<name>` (`peak_von_mises_MPa` at nodes, from the displacements with each part's material; `max_displacement_mm`). `modal[]`: `frequencies_Hz`, `after_step`, `tied` and `free` pairs, `tied_where_closed` (pairs tied on part of their face: nodes, closed fraction), `floating_parts` and `rigid_body_Hz`, and the contact state that step left (`closed_fraction`, `stick_fraction`, `force_N` per pair); `frequencies` is the first modal step's. `contacts.<pair>` gives the law, friction, area, clearance and starting gap.
- **Stabilisation**: parts that no support holds in every direction, and that no bonded contact ties to such a part, get the weak springs to ground (1e-6 of the softest bolt's stiffness, or without bolts 1e-9 E h); `stabilisation.fraction_of_load` (or `fraction_of_preload`) says what they carried.
- **Pictures**: as joints, plus `contact_pressure` on a contact's faces and the mode shapes of the first modal step (`mode: n`); `step` picks a CalculiX step (a modal step shows the state it started from).
- **Benchmarks** (`FEAT_SLOW_TESTS=1`): `assembly_clamp` (an M30 nut at 40 kN on a hub, sleeve and shaft shoulder: the force through both contacts and the nut 40 kN), `assembly_press_fit` (a ring on a shaft, 0.02 mm interference: Lame's contact pressure 78.75 MPa, 10 %), `assembly_bonded_beam` (a cantilever in two bonded pieces: tip deflection F L^3 / 3EI 5 %, first bending frequency 3 %), `assembly_clamped_beam` (the same held by friction under a 50 MPa clamp: closed, and the same deflection and frequency), `assembly_partial_tie` (the whole cantilever held by friction on a base disk 3x its radius: the contact closes on 11 % of the disk's face and the modal run ties it there only; the first frequency must be the clamped cantilever's, 5 %).

**Status (2026-10-16, carbonio: CalculiX from Ubuntu's calculix-ccx, Gmsh 4.15.2, Python 3.14):** with 2026.10.16.3 all 28 tests and all 11 benchmarks pass with CalculiX and Gmsh (`euler_column`, `lame_ring` and `plate_hole` included). On the first run 10 of 11 passed: `lame_ring` met its Lamé values but its equilibrium check was off by 0.1 %, because the loads on support nodes were integrated on flat triangles while CalculiX integrates the curved faces; the face integrals are now isoparametric. The reference solver passes the 9 cases without Gmsh or CalculiX (the exact ones to rounding; cantilever 1.0 %, frequency 0.13 %, pin fin 0.09 %) and a curved quarter ring (bore displacement 0.01 %, equilibrium 1e-8). Buckling was then found to depend on the machine's load (1 of 4 concurrent `euler_column` runs returned 10-21 instead of 674.7): with eigenvalue accuracy 1e-6 and serial buckling jobs (2026.10.16.8), 8 of 8 concurrent runs give 676.25, identical to every digit.

The first CalculiX run confirmed what the translator assumes about it:

- The `.dat` layout: headers `<what> (<components>) for set <SET> and time <t>` (`displacements`, `stresses`, `forces` for RF per node, `temperatures`, `heat generation` for RFL per node).
- Reactions: CalculiX's RF at a node is the external force there (reaction plus applied loads), so the translator subtracts its own equivalent nodal loads and counts each constrained direction of a node once (`gravity_block`, `pressure_cantilever`, `axial_bar` exact). RFL (heat) works the same way, films included (`slab`, `fin_end` exact, `fin_sides` 1 %).
- Face numbers for `*DLOAD P`, `*DFLUX S`, `*FILM F`: the Abaqus/CalculiX convention for tetrahedra (S1 = 1-2-3, S2 = 1-4-2, S3 = 2-4-3, S4 = 3-4-1).

## How it works

1. **Part:** the STEP (or the goal built to STEP).
2. **Mesh** (`mesher.py`): Gmsh (OpenCascade import, one volume, second-order tetrahedra with mid-edge nodes on the geometry, refinement balls); nodes renumbered, Gmsh's documented 10-node order mapped to CalculiX's (the last two mid-edge nodes swap), corners oriented to a positive volume; elements that Gmsh's curving left inverted or nearly so (thin ligaments relative to the element size) get straight edges, and the result says how many (`mesh.straightened_elements`, with a warning).
3. **Faces** (`meshdata.py`): each Gmsh surface's boundary triangles matched to their element faces (S1..S4), outward normals from the element, areas, centres, planarity, cylinder fits; selectors resolved on this data.
4. **Deck** (`deck.py`): nodes, elements, node sets per boundary condition, material, the step (`*STATIC`, `*FREQUENCY`, `*BUCKLE`, `*HEAT TRANSFER`), boundaries, loads (forces as consistent nodal loads of a uniform traction: 0 at triangle corners, A/3 at mid-edge nodes), outputs.
5. **Solve:** `ccx -i <name>` (or the reference solver).
6. **Results** (`results.py`, `runner.py`): the `.dat` and `.frd` read, results computed on the mesh (area-weighted face means are exact for the element interpolation), checks.

The reference solver (`refsolver.py`) is independent element code (isoparametric tetrahedra, collapsed Gauss quadrature, SciPy sparse solvers) that reads the decks this package writes; it checks the deck and result handling without CalculiX.

**Pictures** (2026.10.28.1, as cfd-translator 2026.10.28.1). `"images": true` (the defaults) or a list of views writes `<study folder>/images/<name>.png` after the solve; the result lists them under `images` with what each shows, its colour range, the renderer and the deformation scale. Every run also saves `state.npz` and `state.json` (nodes, elements, the boundary triangles with their CAD-face tags, the nodal fields, each bc's faces and kind, the mode values, the off-BC peak), so `render_images` draws other views later.
- *Views:* `{name, field | mode: n | setup: true, surface: part | <bc name>, deformed: true | scale, view: [elev, azim], clim: [lo, hi] | full | robust, quality: high | basic, slice: {axis, at}}`. Fields: `von_mises`, `displacement` (magnitude, mm), `ux`/`uy`/`uz`, `max_principal`, `safety_factor` (yield / von Mises), `temperature`, `heat_flux` (W/m²), `potential` (V), `current_density` (A/mm²), `e_field` (kV/mm), each where its analysis has it (thermal and joule with `stress: true` add the mechanical ones); validation names the fields a study has. `deformed: true` scales the largest displacement to 5 % of the part's size (the scale is reported); mode views are always deformed and coloured by the relative displacement magnitude; von Mises and safety-factor views mark the off-BC peak. `setup` colours the faces each support and load took, one colour per bc with a legend, to check `selection` by eye. `slice` keeps the part on the low side of the plane and shows the field on the cut.
- *Defaults:* static: von Mises on the deformed part and the setup view; modal: the first 3 modes; buckling: mode 1; thermal: temperature (with `stress`: also von Mises); electric: potential and current density; electrostatic: potential and electric field; joule: temperature, potential, current density.
- *Fields* come from the nodal solution, the same for CalculiX and the reference solver: stresses from the displacements (CalculiX's element formulation, thermal strain included), element means averaged to the nodes by volume; gradients at element centroids, averaged the same way. Mode shapes: the deck now prints each mode's displacements to the `.dat` (`*NODE PRINT U`), and the reference solver writes its eigenvectors.
- *Renderers:* Matplotlib (Agg) by default and as the fallback; VTK through PyVista for `"quality": "high"` (lit, smooth shading with sharp edges kept, curved tet10 surfaces, the volume clipped for slices, white background, vertical scalar bar). VTK draws in a child process (`python -m fea_translator.render_vtk <state dir> <specs.json> <out dir> <name>`, one JSON line back), so an OpenGL crash cannot take down a server or a SLURM job; `probe()` (cached per process) finds EGL, OSMesa or X, else runs the child under `xvfb-run -a`. Without VTK a high-quality view is drawn with Matplotlib, with a warning.

|---|---|---|
| `FEAT_RENDER` | (VTK when it can draw) | `matplotlib`: never VTK |
| `FEAT_RENDER_TIMEOUT` | 900 | seconds for the VTK child process |

**Long runs.** Polling costs the calling model tokens on every call, so pending studies say where they are and how long they still need, and long runs are not polled:

- `progress.<study>`: `stage` (`queued`, `mesh`, `solve`, and with `converge: true` `mesh_fine`, `solve_fine`), `iteration` of `max_iterations` (those steps), `s_per_iteration` (finished steps), `elapsed_min`, `nodes`, `eta_min` (expected minutes left) and `eta_min_max` (at most: the time limit `FEAT_TIMEOUT` of each remaining solve).
- `time_left`: the same for the whole request, with queued studies waiting for a worker; `expected_finish` and `latest_finish` as clock times.
- `next`: under about 5 minutes, call `study_status` again with a `wait_s` that covers it; over 5 minutes, tell the user when the run should finish and stop; collect it later with `study_status` (when the user asks, or from a task scheduled after that time). The server instructions say the same.

The expected time comes from this machine's own finished solves: each run appends its mesh size and mesh and solve times to `timing.jsonl` in the output folder, and a new solve is estimated as (median seconds per nodes^1.5) x nodes^1.5 (sparse direct solver on a 3D mesh); the finer mesh of `converge: true` has about 4.6x the nodes. Before the first finished solve on a machine `eta_min` is unknown and the advice goes by `eta_min_max`.

**SLURM** (2026.10.18.2, the llm-translators contract in `docs/EXECUTION.md`). With `FEAT_EXECUTOR=slurm`, a study estimated at `FEAT_SLURM_MIN_MINUTES` or more (default 1 since 2026.10.30.1, before 5; the size-scaled estimate `validate_studies` reports; a study whose size cannot be told counts as long), or marked `"queue": true`, becomes a SLURM job; the others run in the local pool (`"queue": false` keeps one local). Each job is `<request>/<name>/job.sh` (a complete script: `sbatch job.sh` reruns it by hand) submitted with `sbatch --parsable $FEAT_SLURM_ARGS`; it runs `feat run-study REQUEST NAME` with `--ntasks=1 --cpus-per-task=N`, N = the study's `procs` or `FEAT_PROCS` (default 1), and CalculiX gets `OMP_NUM_THREADS` from `SLURM_CPUS_PER_TASK`; modal and buckling studies always ask for 1 CPU (their eigenvalues are repeatable only single-threaded). Sizing (2026.10.20.1, measured on mochi with `tools/measure_threads.py`: a 175k-node box with the direct solver took 409 / 230 / 167 / 125 s at 1 / 6 / 10 / 19 threads and 6.6 / 12.2 / 12.5 / 14 GB; with the iterative solver 167 s at 1 and at 10 threads and 0.64 GB; a 45k-node box 30 / 21 / 18 s at 1 / 6 / 10): before submitting, feat estimates the mesh's nodes (exact for box parts; for goals and STEP files about 12 nodes per element-size cubed of the part's volume, plus the refinement spheres) and asks for 1 CPU when every solve uses the iterative solver (single-threaded in CalculiX, and now the default above 50,000 nodes), else for the study's `procs` or `FEAT_PROCS` (default 1) capped at a thread per 10,000 nodes. Threads stay optional: CalculiX 2.21's threaded code returned wrong results four times under load (all caught: the stress check, the balance rerun). Memory: `FEAT_SLURM_MEM` (`auto`, default; a size such as `8G`; `none`): where SLURM gives a job that asks for no memory the whole node (`CR_Core_Memory` with `DefMemPerNode=UNLIMITED`, as on mochi), only one job runs at a time, so `auto` asks for what CalculiX needs, fitted to the measurements with a margin: iterative 1 GB + 5.6 kB per node, direct 1 GB + 1.25 × 2.3 GB × (nodes / 50k)^1.43 (half single-threaded), for the larger of the two meshes of `converge`; 8 GB when the size cannot be estimated; a `--mem` in `FEAT_SLURM_ARGS` replaces it, and a job that runs out ends as `out_of_memory`. The job's SLURM time limit (`FEAT_SLURM_TIME`, 2026.11.09.5): `max` (default) asks for the partition's own limit (`UNLIMITED` where it has none; the partition of `FEAT_SLURM_ARGS --partition`, else the default one), since SLURM lets only an admin raise a running job's limit and `extend(request, hours)` then needs only feat's own CalculiX timeout; `timeout` (until 2026.11.09.8 named `estimate`, which still means it) asks for every CalculiX run's timeout plus the meshing and 10 minutes (`converge` doubles the solves, `joule` has 2-3); a number of minutes asks for that (at least the estimate). Either way feat's own timeout ends CalculiX first and writes a clean result; the SLURM limit is the backstop. `extend` raises the job's SLURM limit only when the job's time left (squeue) does not already cover feat's new deadline, and says so when SLURM refuses. `job.json` records the job id; a failed `sbatch` is that study's result (`could not submit: ...`), never a silent local run.

**Per-study run settings** (2026.10.20.3, `docs/EXECUTION.md`, as in cfdt). A study's `"run": {"timeout_s": 30000, "mem": "12G", "procs": 10, "queue": true}` (all keys optional) overrides the machine's defaults for that study only: `timeout_s` replaces `FEAT_TIMEOUT` for each CalculiX solve, counted from when CalculiX starts (an assembly's modal runs get a quarter of it, at least 10 min, each), and sets the job's `--time` (every run's timeout, plus the meshing (at least 10 min a mesh, more for a large expected mesh), plus 10 min); `extend(request, hours)` gives a running study more time; `mem` is the job's `--mem` (any `--mem` / `--mem-per-cpu` in `FEAT_SLURM_ARGS` is dropped for that job, the other arguments kept); `procs` is threads (`--cpus-per-task`, still capped by the mesh size); `queue` as the top-level `queue`. No free-form sbatch arguments. The machine's ceilings `FEAT_MAX_TIMEOUT` (s), `FEAT_MAX_MEM` (e.g. `32G`) and `FEAT_MAX_PROCS` (also bounds the top-level `procs`; unset: no limit) are in `study_format`'s status (`executor.caps`, with the default `timeout_s`); validation rejects values above them (naming the variable), unknown keys, a malformed `mem` (SLURM sizes: `500M`, `8G`) and a `run.procs` / `run.queue` that disagrees with the top-level one. `job.json` records the study's `run`; every result has `execution.limits` = `{timeout_s, mem (the job's, from SLURM_MEM_PER_NODE, e.g. "12288M"; null outside SLURM), from_study: [the run keys set]}`.

**Estimates in validation** (2026.10.22.3, `docs/EXECUTION.md`, for llm-translators' router, `docs/ROUTER.md`). `validate_studies` returns, for each valid study, `"estimate": {"minutes", "procs", "mem_mb"}` from the functions that size its SLURM job: `procs` from `procs_for` (after the size cap; 1 for modal, buckling and iterative solves), `mem_mb` the job's `--mem` (`run.mem`, `FEAT_SLURM_MEM`, else what CalculiX needs), and `minutes` the expected run time: this machine's `timing.jsonl` scaled to the estimated mesh (nodes^1.5) when the records include meshes within 10× of its size, else the mochi measurements (409 s direct single-threaded and 167 s iterative at 175k nodes, direct ~nodes^1.43 / threads^0.4), else the time limit; never above the time limit (every solve's timeout).

**Clusters, stale servers, answers in time** (2026.10.25.1, `docs/EXECUTION.md` "Clusters of several nodes" and `docs/SHARED.md`).
- *Node pinning.* The DGX Sparks (spark-5da5, the controller, and spark-0808) are one SLURM cluster without shared home folders, so a job must run on the node that submitted it. `FEAT_SLURM_NODE=local` (default) adds `--nodelist=<this node>` to every job (in `job.sh`) when `scontrol -o show node` lists several nodes; this node is the one whose `NodeName`/`NodeHostName` is the host name, else whose `NodeAddr` is one of the machine's addresses (`hostname -I`: the Sparks' Tailscale addresses). `any` adds nothing (shared homes); a node list is used as given; a `--nodelist`/`-w` in `FEAT_SLURM_ARGS` wins. `tool_status().executor.node` = `{setting, nodelist, cluster_nodes, this_node}` (`nodelist` null when SLURM may choose; the router's `sbatch --test-only` asks the same), and `executor.node_cores`: threads are capped at this node's cores (CPUs / threads per core), never the cluster's.
- *Settings.* `FEAT_SLURM_ARGS` is split with `shlex` ("--mem=8G --nodelist=spark-5da5" is two options); its `--mem`/`--mem-per-cpu` wins over `FEAT_SLURM_MEM` and its `--nodelist`/`-w` over `FEAT_SLURM_NODE`, detected from the words, not by substring.
- *SLURM that does not answer.* `scontrol` answers are kept for a minute; a failure is asked again, but not within 5 s (2026.11.09.8: a dead controller costs one timeout per call). A failing `squeue` (controller down) leaves jobs `unknown` and pending; before, they were taken as gone and reported `failed`.
- *Stale servers.* A server started by `main()` from a shared release (`<prefix>/releases/<name>/` with `RELEASE.json`) notices when `<prefix>/current` points to another release: while idle it refuses a call with `STALE_SERVER` and exits (the router repeats the call on a new server), and an idle stale server exits by itself within ~20 s; a busy one answers with a `server_stale` note and exits once idle. `FEAT_EXIT_WHEN_STALE` = 1 (also personal checkouts) / 0 (never). Tests and `run-study` in a release that is not yet current run normally.
- *Answers in time.* Every tool runs in a worker thread under a 48 s deadline: SLURM commands, `sbatch` and the waits of `run_studies`, `study_status`, `run_benchmarks`, `bench_status`, `jobs`, `cancel` use only the time left (a submission that cannot finish in time fails clearly). Part sizes for goals and STEP files (CAD) are computed in a worker process (at most 20 s; a late answer is kept), and `get_deck` meshes in a worker process (after 45 s it answers `pending` with the deck's path). Solves run in the worker pool or in SLURM jobs, as before.

A SLURM study's state comes from the files and the queue only, so `study_status` works from any server process, after restarts and from other conversations: `done` (`<name>.json`, written atomically), `queued` (`reason`, `expected_start`, `ahead`), `running` (the progress above plus `job_elapsed_min`), and the final `timed_out`, `out_of_memory` (add `--mem=` to `FEAT_SLURM_ARGS`), `cancelled` and `failed` (the last 30 lines of `job.log`), which move the study into the results with `ok: false`. One `squeue` call per status; `sacct` for jobs that left the queue without a result, else `job.log` (SLURM's "DUE TO TIME LIMIT" and "CANCELLED" lines). `tool_status` reports `executor: {kind, sbatch, min_minutes, procs, time_limit_min}`. Command line: `feat run-study REQUEST NAME`, `feat jobs [--limit N] [--active]`, `feat cancel REQUEST [NAMES...]`. Tested with fake `sbatch`, `squeue`, `scancel`, `sacct`, `sinfo` and `scontrol` (llmt-runtime's merged fake, `llmt_runtime.testing`, since 2026.11.09.8): submit, running, done collected by a new process, queued, every final state from `sacct` and from `job.log`, cancel, `jobs`.

In the Claude desktop app's `claude_desktop_config.json` (or LM Studio's `mcp.json`), next to `b3dt`:

```json
{"mcpServers": {"feat": {"command": "/Users/<you>/Desktop/fea-translator/.venv/bin/feat-mcp"}}}
```
